# Политики трафика контейнера для Xray TUN

Экран управляет Linux внутри контейнера 3x-ui. RouterOS mangle, routing tables,
NAT и выбор трафика, поступающего в контейнер, настраиваются на MikroTik отдельно.
Текущий вариант поддерживает IPv4; существующие IPv6-настройки не меняются.

## Включение

1. Обновите образ. Цель Docker `routeros` содержит `iproute2` и `nftables`.
2. Добавьте в envlist контейнера `XUI_ENABLE_POLICY_ROUTING=true` и перезапустите его.
3. Откройте **Политики контейнера**. Панель покажет интерфейсы и причину, если
   ядро, инструменты или права не позволяют управлять маршрутизацией.
4. Внутри контейнера должен быть включён `net.ipv4.ip_forward`. Панель читает
   значение и откажется включать пересылку при выключенном forwarding.
   Если RouterOS разрешает изменение, в shell контейнера:

   ```sh
   sysctl -w net.ipv4.ip_forward=1
   ```

   Сохранение sysctl после пересоздания контейнера зависит от вашего запуска.
   Панель не изменяет sysctl, NAT или firewall RouterOS автоматически.

`CAP_NET_ADMIN` и поддержку `nf_tables` должен предоставлять сам RouterOS.
Установка утилит не предоставляет эти возможности ядра. Docker-флаги вроде
`--cap-add` из Linux-примеров не являются командами RouterOS. При отсутствии
прав/поддержки применение останется недоступным.

## Интерфейсы и действия

- **Входящий по умолчанию** — интерфейс поступления пакетов от RouterOS, обычно
  `eth0`. В отдельном правиле можно указать другой входящий интерфейс.
- **TUN** — интерфейс Xray. В этом upstream имя по умолчанию `xray0`; проверьте
  поле `name` своего TUN и список интерфейсов панели.
- **Прямой uplink** — физический/veth-интерфейс выхода, отличный от TUN.
- **Шлюз uplink** — IPv4 next hop этого интерфейса. Для включённого действия
  прямого выхода это обязательное значение, например адрес RouterOS на veth.

| Действие              | Поведение                                                                                                 |
| --------------------- | --------------------------------------------------------------------------------------------------------- |
| TUN                   | Марка выбирает таблицу с default route на заданный TUN                                                    |
| Прямой uplink         | Марка выбирает отдельный default route через шлюз и uplink                                                |
| Обычная маршрутизация | Обработка правил панели прекращается; пакет сохраняет прежнюю марку и следует существующим правилам Linux |

Срабатывает первое включённое правило сверху вниз. Пустые адреса/порты означают
любое значение. Поддерживаются IPv4-адреса, канонические CIDR, `tcp`, `udp`,
`icmp` и любой протокол. Порт — число `1–65535` или диапазон `1000-2000`, только
для TCP/UDP. Новые правила создаются выключенными.

Несовпавшие пакеты тоже сохраняют существующую маршрутизацию. Чтобы через TUN
шёл только выбранный трафик, добавьте последним включённое правило **Прямой uplink**
без фильтров. Это важно при широких `autoSystemRoutingTable` Xray: upstream
добавляет эти маршруты в основную таблицу Linux. Панель не переписывает настройки
TUN и автоматические маршруты Xray.

Исходящие соединения самого прокси не маркируются: цепочки OUTPUT здесь нет.
Настройка исходящего интерфейса Xray (`autoOutboundsInterface`) остаётся прежней.

## Пример для личного роутера

Допустим, LAN — `192.168.88.0/24`, вход в контейнер — `eth0`, TUN — `xray0`,
прямой next hop RouterOS на veth — `172.17.0.1`. Подставьте свои значения.

1. Выберите эти интерфейсы и шлюз.
2. Добавьте включённое правило: источник `192.168.88.0/24`, протокол TCP,
   порт назначения `443`, действие **TUN**.
3. Последним добавьте включённое правило без фильтров **Прямой uplink**.
4. Включите политику, откройте предпросмотр, проверьте интерфейсы и правила,
   затем нажмите **Применить и сохранить** в окне подтверждения.

Для фильтрации по LAN-адресам RouterOS должен сохранять их при передаче
в контейнер. Если перед контейнером выполнен src-nat, Linux увидит изменённый
источник. Пакеты, вернувшиеся с uplink контейнера на RouterOS, следует исключить
из повторного направления в контейнер; обычно RouterOS mangle ограничивают
входящими LAN-интерфейсами. Это предотвращает петлю для прямого выхода.

## Какие объекты меняются

| Объект               | Значение                                                           |
| -------------------- | ------------------------------------------------------------------ |
| nftables             | `table inet xui_policy`, цепочка PREROUTING с приоритетом mangle   |
| Марка TUN            | `0x3e010000/0xffff0000`                                            |
| Марка прямого выхода | `0x3e020000/0xffff0000`                                            |
| Таблицы IPv4         | `10001` — TUN, `10002` — uplink                                    |
| Приоритеты `ip rule` | `100` и `101`; системный `local` с приоритетом 0 сохраняется       |
| Протокол маршрутов   | `242`                                                              |
| Default routes       | Рабочий маршрут с metric 10, запасной `unreachable` с metric 32767 |

Для совпавших пакетов панель управляет старшими 16 битами марки; младшие 16 бит
сохраняются. Зарезервированные значения нельзя одновременно использовать для
другой политики. При занятых таблицах/приоритетах или чужом `xui_policy` панель
откажется применять конфигурацию. Основная таблица, посторонние маршруты и
firewall не очищаются. Существующие `ip rule` с приоритетом меньше 100 сохраняют
своё первенство; их можно увидеть в состоянии ядра.

Если TUN исчезает, рабочий маршрут удаляется ядром, а `unreachable` не даёт
выбранному трафику уйти через обычный default route. После появления работающего
интерфейса панель восстановит маршрут при следующей проверке (обычно до 5 секунд).
Она не создаёт сам TUN.

## Сохранение и статистика

Конфигурация хранится ключом `nativePolicyRouting` в таблице `settings`.
Редактирование формы, предпросмотр и опрос состояния не записывают SQLite.
Явное применение проверяет параметры, права, владение объектами и синтаксис nft,
сохраняет желаемую конфигурацию, затем применяет её. При ошибке предпринимается
откат правил и конфигурации; ошибка отката также возвращается пользователю.

После перезапуска панели политика восстанавливается. Постоянная проверка
сравнивает конфигурацию и индексы интерфейсов; стабильное состояние не вызывает
системных команд и записи настроек. Выключенная сохранённая политика очищает
свои объекты, в том числе после прерванного отключения. Перед удалением переменной
включения сначала выключите политику через панель.

Пакеты и байты читаются из nftables каждые 5 секунд только при открытом экране.
Это счётчики ядра: SQLite и файлы истории не обновляются. Применение/восстановление
пересоздаёт цепочку и сбрасывает счётчики. Для несохранённых изменений цифры
скрыты, чтобы не приписывать старые счётчики новым правилам.

API администратора: `GET /panel/api/policy-routing`,
`POST /panel/api/policy-routing/preview`, `POST /panel/api/policy-routing/apply`.
Токены monitor/node-sync/node-admin к ним не допускаются. Строки команд от
пользователя не принимаются; shell для выполнения правил не используется.

## Проверки и перенос

ARM64 workflow запускает нативный тест в отдельном контейнере с `--network none`
и `CAP_NET_ADMIN` до публикации. Проверяются реальные TCP/UDP-пакеты, сохранение
младших бит марки, выбор таблиц, rollback, пересоздание интерфейса, восстановление
после прерванного отключения и сохранность посторонних маршрутов.
Veth заменяет устройство TUN: аппаратную проверку RouterOS/Xray TUN нужно выполнить
отдельно.

При переносе сохраните `internal/policyrouting`, сервис/контроллер, регистрацию
API и задания, страницу React и пакеты образа. Сравните новые правила upstream
и повторите тест workflow в отдельном сетевом пространстве. Не запускайте нативный
тест в рабочем сетевом пространстве роутера.
